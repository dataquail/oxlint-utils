---
title: Members
description: Constraining the names a file may declare on a type, or call.
---

`members` restricts the names appearing inside a file, in one of two positions. It is how a
policy states a _vocabulary_ — a set of names a stereotype is allowed to use — where the
constraint is not about which modules are reached at all.

```js
"*.repository.ts": {
  members: [
    {
      message:
        'A repository port method named "{name}" is a query in disguise. A port ' +
        "loads and saves an aggregate by identity; anything keyed on another " +
        "column is a read model, and belongs in queries/.",
      subject: "type-members",
      in: "*RepositoryShape",
      match: "find*",
      matchNot: ["findOneById", "findManyByIds"],
    },
  ],
},
```

| Field      | Meaning                                                            |
| ---------- | ------------------------------------------------------------------ |
| `subject`  | `"type-members"` or `"calls"`                                      |
| `in`       | for `type-members`, globs against the declaration's own name       |
| `match`    | names the rule is about. Omit to mean every name in that position  |
| `matchNot` | names carved back out of `match`                                   |
| `allow`    | names permitted; anything matched and not allowed is the violation |
| `message`  | why. `{name}` is substituted with the offending name               |
| `probe`    | `{ source, name }` — a snippet the rule must report `name` out of  |

`match`/`matchNot` narrow _what the rule is about_; `allow` says which of those are fine.
Either side can carry the exemption — the `find*` example above uses `matchNot`, and a hook
allowlist below uses `allow` — and which reads better depends on whether the exceptions are
the interesting part.

## `type-members`

The names declared on a type literal, with `in` selecting the declaration they sit in:

```ts
type UserRepositoryShape = {
  readonly findOneById: (id: UserId) => Effect<UserRoot>;
  readonly findOneByEmail: (email: string) => Effect<UserRoot>; // ← reported
};
```

A computed key is skipped: it is not a name a vocabulary rule can speak about.

## `calls`

Called identifiers and called members — `useState(0)` and `React.useEffect(fn)` both
produce a site named for the callee:

```js
"*.view.tsx": {
  members: [
    {
      message: "`{name}` puts state in the View. It belongs in the ViewModel.",
      subject: "calls",
      match: "use[A-Z]*",
      allow: ["useAtomValue", "useAtomSet", "useAtomSuspense", "useId", "useCallback"],
    },
  ],
},
```

The `use[A-Z]*` pattern is the reason [character classes](/oxlint-utils/architecture-rules/manifest/patterns/)
exist in the glob language: it means _a hook_, without also matching `user` or `useful`.

:::note
`calls` is a syntactic check on the callee's name, not a type-directed one. It cannot tell
`useState` imported from React apart from a local function of the same name — which is the
right trade for a rule about a naming convention, since the convention is what it is
policing.
:::

## Which declarations are read

`type-members` reads the members **written in** a named type declaration, under that
declaration's name — a `type` alias or an `interface`, and inside an alias, through
intersections, unions and parentheses:

```ts
type Base = { save(): void };
type Port = Base & { findOneById(): void }; // Port.findOneById — and Base.save, under Base
interface Other extends Base {
  findMany(): void;
} // Other.findMany
```

A reference is not followed. `Base`'s members are declared where `Base` is and are reported
there under its own name; following the reference would report every member twice, under
two names. So an `in` pattern must name the declaration where the member is actually
written.

Not read: class bodies (a class is not a type declaration — a runtime object with
visibility is a different vocabulary question), index, call and construct signatures, mapped
types, and computed keys.

## Proving the rule reads your shape

A rule about a shape the extractor does not read would pass its generated probe while
reporting nothing.

An authored `probe` closes that: the snippet is parsed at load, and the rule must report
`name` out of what the parser read, or the policy refuses to load.

```js
probe: {
  source: "export type TodosRepositoryShape = { findOneByEmail(): void };",
  name: "findOneByEmail",
},
```

Write it in the shape your real ports take. See
[Probes](/oxlint-utils/architecture-rules/enforcement/probes/#writing-the-probe-yourself).

## Several rules on one node

`members` is an array, and each entry is compiled to its own rule with its own probe. A
node that constrains both what it declares and what it calls states both, and a violation
names which one fired.
